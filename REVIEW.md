# Kwenta — full-project review

Reviewed from the files you shared (the GitHub repo itself isn't reachable from here, so anything that exists only there — e.g. `.env.example`, `public/`, the empty `legacy-sql/*.sql` files — wasn't inspected). I read the code; I could not run it, so please test on your phone after applying.

Each item is labelled **[bug]** (wrong behaviour), **[security]**, or **[cleanup]**. Where the right answer is a judgment call rather than a rule, it says so.

## How to apply (order matters)

1. **Copy the delivered files into the repo at the same paths** (they're laid out as `src/…`, `public/…`, `supabase/migrations/…`, `scripts/…`, plus `index.html` and `README.md` at the root).
2. **Run the patch script:** `node scripts/apply-patches.mjs --dry`, then without `--dry`. It edits ~20 other files by exact match and refuses to touch any file that doesn't match, so nothing can end up half-patched.
3. **Review, then apply the migration:** `npm run db:push` (try it on a Supabase branch first — sections 6–7 change function privileges).
4. **After the first deploy**, existing installs will show the "A new version is ready — Update" banner once (see item 14).
5. Delete `scripts/apply-patches.mjs` when done.

## Found but NOT changed — your call

These are design decisions, not clear bugs.

1. **Cached data can cross accounts.** On boot while signed out, the old on-device cache is loaded "so it can be moved into the account on first sign-in." If a session was ended server-side while the app was closed (so no logout cleanup ran), and someone else then signs up on that device, the previous person's cached data is uploaded into the new empty account. _Rule-of-thumb fix:_ tag the cache with its owner's id. _Simpler:_ clear the cache on boot when signed out — but that drops the one-time upgrade path for anyone who used Kwenta before accounts were required. Your call.
2. **Restoring a backup inside a household duplicates other members' entries** (the backup doesn't record who owned what). Safest short-term: hide Restore while in a household. Proper fix: save `userId` in backups and only restore your own rows.
3. **Joining a household shares all your existing personal entries** (not salary) with no confirmation. Probably wants a confirm step.
4. **Leaving a household then setting a budget** for a category you'd created there can overwrite the household's row (budgets are keyed `(user_id, category)`). Needs a schema change.
5. **`tabsShared.css` uses `!important`** to force one border radius. Folding it into `style.css` is cleaner but touches many selectors — I left it.
6. `appLockSheet.js` still has a "guest" branch that can't run (no guest mode); `profilePage.js` shows "Plan" twice. Harmless.
7. Error messages are inserted into some sheets without `escapeHtml` (2FA, devices, backup, password). They come from Supabase or your own strings, not from users, so I treated it as hygiene rather than a bug.
8. The empty `supabase/migrations/20261006024805_remote_schema.sql` duplicates the real baseline. Only delete it if `npm run db:list` doesn't list that version as applied remotely; otherwise run `npx supabase migration repair` first.
9. Run `select jobname, schedule, command from cron.job;` once. I made both bill-reminder functions safe whichever one is scheduled, but I can't see your schedules.

## Structure — recommended, not applied

Moving files breaks imports across the app, so I kept paths. If you want to go further, the natural split is by feature: `src/features/{bills,goals,utang,budgets,household,security}/` each holding its logic + tab + sheet. Do it one feature at a time with a build between each.
